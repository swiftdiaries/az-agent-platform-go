### Task 1 confirmed MCP transport

The user confirmed stateful Streamable HTTP with an MCP session ID. Task 1 uses `mcp.StreamableClientTransport` and a stateful server (`StreamableHTTPOptions.Stateless` remains `false`). The integration fixture proves one nonempty `Mcp-Session-Id` is reused within a run and different runs get different sessions. A per-run `http.Client` copies only the server registry's configured headers, so OAuth/session-cookie header names remain deployment configuration rather than platform constants. Legacy HTTP+SSE is not the selected transport.

`configs/journeys.yaml` deliberately uses JSON syntax, which is valid YAML 1.2, so strict decoding and unknown-field rejection need no additional parser dependency. If configuration authors later require YAML-only syntax, add a YAML parser as a separate compatibility change rather than silently accepting a subset.

The checked-in MCP server entry is also the credential-free startup contract for tool names. Journey allowlists must match that catalog exactly, then each run still performs authenticated discovery and exact binding. HTTP 401/403 from the downstream MCP transport is classified as `auth_required`; other transport/model failures remain sanitized terminal failures. The application trace chain is `chat.accept` → `agent.start_turn` → `hub.route` and `journey.run`, with provider and MCP children. The stable product call ID is generated from the run and carried in the MCP header, event, and span; a distinct provider call ID remains inside MAF history for function-result correlation.

The per-run MCP HTTP client rejects redirects before a second request so configured credential headers cannot be replayed to another origin. At Chat ingress, authenticated-principal plus external thread/run identity maps to stable process-local opaque thread, run, and communication IDs. Only opaque IDs enter Agent state and telemetry; AG-UI events translate back to the request's external thread/run IDs at the response edge. Task 2 replaces this process-local mapping with durable records.

## Exact MAF seams

- Session: `a.CreateSession(ctx, opts...) (*agent.Session,error)`; JSON round trip uses `json.Marshal(session)` and `json.Unmarshal(data,&session)`; run with `a.RunText(ctx,text,agent.WithSession(session)).Collect()` or `RunMessage`.
- Tool loop: `toolautocall.New(toolautocall.Config{AllowConcurrentInvocations:false, MaximumConsecutiveErrorsPerRequest:&zero})`. Approval binding remains enabled; do not set `DisableApprovalResponseBinding`.
- Approval: wrap `tool.FuncTool` with `tool.ApprovalRequiredFunc(fn)`; inspect `*message.ToolApprovalRequestContent`; the authoritative request creates `request.CreateResponse(approved, reason)`.
- AG-UI adapter: `aguiprovider.NewJSONHTTPHandler(a, aguiprovider.HandlerConfig{}) http.Handler`. It maps one HTTP run to SSE and does not provide the platform's durable session, detached execution, snapshot/replay, or ownership semantics.
- MCP: `mcptool.Connect(ctx, transport)` and `mcptool.ListTools(ctx, session)`; the wrapper ultimately calls `session.CallTool(ctx,&mcp.CallToolParams{Name: originalName, Arguments: json.RawMessage(args)})`. A Go error is transport/dispatch failure. `CallToolResult.IsError` is a successfully returned protocol-level application error and must be classified separately.
- Streamable HTTP OAuth: `mcp.StreamableClientTransport{Endpoint: endpoint, OAuthHandler: handler}`. Product header forwarding uses a per-run `http.RoundTripper`; never mutate a global client.
- OTel: `agent.Config{Middlewares: []agent.Middleware{otelprovider.NewMiddleware(otelprovider.MiddlewareConfig{SourceName: "az-agent-platform"})}}`; keep sensitive-data logging disabled.
- Skills: `skills.NewContextProvider(skills.ContextProviderOptions{Sources: []skills.Source{fsskills.NewSource(os.DirFS(root))}})`. Built-in skill tools require approval by default. This platform does not expose script execution; Task 5 provides a restricted source and only load/read tools.

Portable source detail is in [references/framework-baseline.md](references/framework-baseline.md); preserved spike artifacts are in [references/spike/README.md](references/spike/README.md).

## Evidence limits

The qualified spike established session JSON persistence, native approval binding, typed clarification glue, fresh in-memory credential forwarding, and the counterexample where an ambiguous mutation can be issued twice through unconstrained autocall. It did not establish durable AG-UI hosting, exact concurrent correction consumption, Kubernetes ownership, Java trace propagation, or crash-midtool recovery. Tasks 2–6 close the adopted seams with product tests; crash-midtool automatic continuation remains excluded.

## Task 3 ownership and steering evidence

- Context7 resolved PostgreSQL and queried `/websites/postgresql_16` for row locks and current database time. `clock_timestamp()` is evaluated in a separate statement after conversation/run locks, rather than transaction-start `now()`. Claim accepts only an explicit admitted pending run and its original command. Conversation epochs increase on claims; running ownership is never transferred. All owned journal mutations require the matching owner, epoch, live state, and unexpired lease. Unclaimed pending admissions also expire, so a crash between admission and claim cannot leave permanent live work.
- Admission preserves the original command/run/communication receipt and adds `ExecutionRunID`. Commands admitted while a compatible journey is live join its ordered inbox; admission after terminal commit creates a fresh pending run. `Finish` shares the conversation lock, returns `ErrPending` if successful completion would strand input, and the controller calls it directly. That owner drains again using its local headers and uncommitted history. Reaping records `interrupted` only. A fresh authorized ingress can start a new run; retries and pending corrections on an interrupted run cannot restart it.
- Each actual `Model.Complete` request exposes handoff, selected conversation context (the latest completed turn outside the selected journey), retained provider history, and ordered pending commands. MAF receives the full explicit message history for each invocation. Context7's MAF result covers multiple languages; exact Go behavior was checked in the pinned fork's `agent/agent.go:269` and `:485`: an auto-created session does not retain the default history provider. No framework session is persisted. `command.included` is committed only after the actual model boundary has observed the request; failed inclusion commits abort before tool dispatch and retain pending input without a success claim.
- Context7 `/ag-ui-protocol/ag-ui` documents `NewCustomEvent(name, WithValue(value))`. Chat resolves a steering command's external run ID to the Agent execution run using authoritative snapshot mappings. Snapshots expose pending-command counts and interruption, and all later committed domain events are emitted with their journal sequences. The three-replica test asserts uninterrupted ordered SSE IDs after the snapshot watermark.
- Context7 `/modelcontextprotocol/go-sdk` documents call-context cancellation and Streamable HTTP client customization. Pinned SDK v1.7.0 `mcp/streamable.go:2722` sends session-close DELETE using its session context, which can outlive the owning run. The renewal-failure regression first hung there when the remote fixture ignored cancellation. The shared HTTP transport now combines request and run lifetime and releases that binding when the response body closes. The regression proves local shutdown completes while remote work remains blocked, then rejects the late remote result. This does not claim remote cancellation or classify effect outcomes (Task 4).
- Task 1 stateful MCP initialization/session IDs, configured cookie/OAuth headers, redirect rejection, trace privacy, principal isolation, and Task 2 durable history/replay remain covered by the existing full and race suites. Task 4 interaction/effect semantics, Task 5 skills/retained bundle rollout, and Task 6 real Foundry/Java/Kubernetes acceptance remain outside this submission.

### Task 3 terminal-command disposition repair

- Specification review found that `failed`/`auth_required` could commit while accepted corrections remained indefinitely pending. Successful finish still returns `ErrPending` for a live-owner drain. Failed/auth-required finish now atomically records `command.rejected` for each unincluded command with the exact terminal run reason; owner-loss reaping records `command.interrupted`. Both paths use the existing conversation/run lock and transaction. They neither claim inclusion nor schedule provider/tool reentry.
- Migration `000003_command_dispositions.sql` adds a constrained terminal reason without changing earlier migration checksums. Pending selects exclude disposed commands, and the database prevents simultaneous inclusion and terminal rejection. Existing unincluded terminal commands receive explicit terminal reasons during migration. Snapshot command outcomes distinguish pending, included, rejected, and interrupted; Chat emits disposition/reason in snapshots and subsequent events, preserving external thread/run correlation.
- A false inclusion flag means no committed inclusion record; it is not proof the provider never saw a request. In particular, an inclusion-commit failure can follow actual provider observation. Its command is terminally rejected with reason `failed`, and the integration test proves no automatic provider retry. Reconnect above the watermark restores the command disposition directly from the snapshot.
- Barrier coverage now forces both admission/finish orders for completed, failed, and auth-required outcomes. Failure-first admits a fresh pending run only for that new ingress; admission-first rejects the queued correction without retrying it. Injected failure of the final terminal event proves command dispositions, their events, and run termination roll back together for failure, auth-required, and owner interruption.

### Task 3 Chat command-correlation repair

- Quality review found that opaque Agent communication IDs were emitted without a usable AG-UI command correlation. Chat now reads its durable reverse mapping from `chat_runs` joined to `chat_threads`, constrained by authenticated principal and internal thread. One query projects all snapshot command outcomes; a live stream reloads that mapping only when an unfamiliar newly admitted command appears. No additional durable projection, shared cache, or Agent identity change was added.
- Snapshot `commands[].runId` and live `command.*` custom-event `value.runId` identify the original external run ID supplied for that command. The enclosing stream retains the external run ID used to observe its authoritative execution. Internal communication IDs stay inside the Chat/Agent boundary. Missing mappings produce a sanitized observation failure rather than exposing an opaque fallback or attributing another command's outcome to the observed command.
- HTTP coverage now checks two distinct steering commands for included, rejected, and interrupted outcomes in POST streams and above-watermark reconnect snapshots from newly constructed Platform/Chat replicas. It verifies external command correlation separately from the execution envelope, absence of internal communication IDs at the edge, principal isolation, and no model/tool reexecution during reconnect.
